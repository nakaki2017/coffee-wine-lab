# 液体风味公式 成本与盈利模式

版本：1.0  
日期：2026-06-14  
范围：Web MVP、Supabase 后端、未来可能的 AI / 收费功能  

## 0. 结论先说

MVP 成本可控。

原因很简单：

1. 当前产品不需要自建服务器。
2. 当前 MVP 不接 AI，所以 API 成本接近 0。
3. 前端是静态 Web，可以用 Cloudflare Pages / Vercel 免费档起步。
4. 后端使用 Supabase，早期用户量小的时候可以从免费档或低价 Pro 档起步。
5. 真正需要盯住的成本是照片存储和照片流量。

建议策略：

1. MVP 阶段先不收费。
2. 先验证用户是否愿意持续记录。
3. 当出现高频用户和明显存储成本后，再上 Pro 订阅。
4. AI 功能后置，并且必须按次数或额度控制。

一句话：先把产品做成用户愿意记的工具，再谈收费。现在就做复杂支付，会拖慢节奏。

## 1. 成本结构

### 1.1 成本分层

| 类型 | 当前 MVP 是否需要 | 说明 |
| --- | --- | --- |
| 域名 | 需要 | 约 $10-20 / 年，取决于后缀和注册商 |
| 前端部署 | 需要 | 静态站可免费起步 |
| 数据库 | 需要 | Supabase Postgres |
| 登录认证 | 需要 | Supabase Auth |
| 文件存储 | 需要 | 日历照片 / 拉花图 |
| 邮件发送 | 可选 | 注册、找回密码、通知。MVP 可先依赖 Supabase 默认能力 |
| AI API | MVP 不需要 | 后续做 AI 复盘才需要 |
| 支付系统 | MVP 不需要 | 有收费功能后再接 |
| 监控 / 日志 | 可选 | 早期可用免费工具，出问题再补 |
| 备案 / 合规 | 视部署地区 | 国内服务器和小程序会复杂很多；海外静态站相对轻 |

### 1.2 固定成本

| 项目 | 保守选择 | 月成本估算 | 备注 |
| --- | --- | ---: | --- |
| 域名 | Cloudflare Registrar / Namecheap 等 | $1-2 | 按年付，均摊到月 |
| 前端部署 | Cloudflare Pages Free | $0 | 静态请求和带宽免费额度非常友好 |
| 后端 / 数据库 | Supabase Free 或 Pro | $0-25 | 免费档可验证；Pro 更稳 |
| 图片存储 | Supabase Storage | $0 起 | 超出额度后按官方价格计费 |
| 支付 | Stripe / Lemon Squeezy / Paddle | $0 固定 | 按交易抽成 |
| AI | 不接 | $0 | MVP 不做 |

MVP 早期固定成本大致：

```text
免费档试跑：$1-2 / 月
稳定小规模：$26-30 / 月
```

这里的稳定小规模主要是假设：
- 域名约 $1-2 / 月。
- Supabase Pro 约 $25 / 月。
- 前端仍用 Cloudflare Pages 免费档。

Supabase 具体价格、免费额度和超额费用以上线前官方页面为准。

## 2. 服务器成本是否可控

### 2.1 前端部署

当前项目是 Vite + React，构建后是静态资源。

可选方案：

| 平台 | 成本 | 适合阶段 | 说明 |
| --- | ---: | --- | --- |
| Cloudflare Pages Free | $0 | MVP / 早期 | 免费档包含 500 次构建 / 月、无限静态请求、无限带宽 |
| Vercel Hobby | $0 | MVP / 个人项目 | 免费起步，适合快速部署 |
| Vercel Pro | $20 / 月起 | 稍复杂的生产项目 | 包含更多用量和团队协作能力 |

建议：

1. MVP 先用 Cloudflare Pages。
2. 如果需要更顺手的预览部署、团队协作、Vercel 生态，再考虑 Vercel。
3. 当前没有 SSR，不需要函数计算。

### 2.2 Supabase 成本

当前使用 Supabase：

1. Auth：登录 / 注册。
2. Postgres：豆种、批次、冲煮、杯测、做法、日历记录。
3. Storage：日历照片。

成本判断：

1. 数据库文本数据非常小。
2. 行数增长也慢。
3. 最大变量是 Storage 图片。
4. Supabase 免费档可以验证 MVP，但正式长期使用建议上 Pro。

数据库体积估算：

假设 1 个重度用户一年：

| 数据 | 年量 | 单条粗略大小 | 年体积 |
| --- | ---: | ---: | ---: |
| 豆种档案 | 100 条 | 2 KB | 200 KB |
| 购买批次 | 100 条 | 2 KB | 200 KB |
| 冲煮记录 | 365 条 | 3 KB | 1.1 MB |
| 杯测记录 | 200 条 | 3 KB | 600 KB |
| 日历文本 | 365 条 | 1 KB | 365 KB |

结论：

```text
文本数据库不是成本问题。
图片才是成本问题。
```

### 2.3 图片存储成本

日历照片是变量成本核心。

假设：
- 用户每天上传 1 张照片。
- 压缩后每张 300 KB。
- 每月 30 张。

单用户每月图片新增：

```text
300 KB * 30 = 9 MB / 月
```

规模估算：

| 用户数 | 每人每月图片 | 每月新增存储 |
| ---: | ---: | ---: |
| 100 | 9 MB | 900 MB |
| 1,000 | 9 MB | 9 GB |
| 10,000 | 9 MB | 90 GB |

如果不压缩，按每张 2 MB：

| 用户数 | 每人每月图片 | 每月新增存储 |
| ---: | ---: | ---: |
| 100 | 60 MB | 6 GB |
| 1,000 | 60 MB | 60 GB |
| 10,000 | 60 MB | 600 GB |

结论：

1. 必须压缩图片。
2. 必须限制单张大小。
3. 免费用户必须限制图片上传量。
4. 付费权益可以围绕图片容量做。

建议 MVP 限制：

| 用户类型 | 图片能力 |
| --- | --- |
| 免费用户 | 每月 30 张，单张压缩到 500 KB 内 |
| Pro 用户 | 每月 300 张，单张压缩到 1 MB 内 |
| 超额 | 提示升级或下月恢复 |

## 3. API 成本是否可控

### 3.1 当前 MVP

当前 MVP 没有 AI API。

所以：

```text
OpenAI / 其他 AI API 成本 = $0
```

Supabase 查询本质上是后端服务用量，不单独按“API 调用”理解。真正要看的是：

1. 数据库大小。
2. Storage 存储。
3. 带宽。
4. 认证用户数量。

### 3.2 未来 AI 成本

如果后续做 AI，建议只做三类：

1. 基于用户历史冲煮记录生成复盘。
2. 基于一支豆子的多次冲煮记录给调整建议。
3. 基于杯测标签生成风味总结。

不建议早期做：

1. 图片识别拉花评分。
2. 自动杯测打分。
3. 大段聊天式咖啡顾问。

AI 成本估算要按 token 算。

假设一次 AI 复盘：
- 输入：3,000 tokens。
- 输出：800 tokens。
- 每个活跃付费用户每月用 20 次。

则每用户每月：

```text
输入 60,000 tokens
输出 16,000 tokens
```

如果使用低成本模型，单用户 AI 成本通常可以控制在几美分到几毛美元区间。若使用高端推理模型，成本会明显上升。

建议：

1. 免费用户不提供 AI，或每月 3 次。
2. Pro 用户每月固定 AI 次数，例如 50 次。
3. 超额按包购买。
4. 每次 AI 任务必须记录 token 和成本。
5. 所有 AI 功能必须有服务端限额，不允许前端自己判断。

### 3.3 AI 成本红线

建议红线：

```text
单个 Pro 用户每月 AI 成本 <= 订阅价格的 20%
```

举例：

若 Pro 定价 $3.99 / 月，则 AI 成本最好低于 $0.8 / 用户 / 月。  
如果超过，需要减少次数、换模型、做缓存或涨价。

## 4. 时间成本是否可控

### 4.1 当前已完成基础

当前项目已经有：

1. React + Vite 项目。
2. Supabase 客户端。
3. 登录。
4. 豆种档案。
5. 库存批次。
6. 冲煮记录。
7. 杯测记录。
8. 做法模板。
9. 日历。
10. 中英文切换。
11. 基础统计。

所以产品不是从 0 开始。

### 4.2 上线前剩余时间估算

| 工作 | 估算 | 说明 |
| --- | ---: | --- |
| UI 细节打磨 | 1-3 天 | 移动端适配、中文日期、空状态 |
| Supabase 项目配置 | 0.5-1 天 | env、migration、RLS 检查 |
| 图片压缩和上传限制 | 1-2 天 | 强烈建议上线前做 |
| 部署和域名 | 0.5 天 | Cloudflare / Vercel |
| 基础埋点 | 0.5-1 天 | 至少记录核心漏斗 |
| 支付功能 | 3-7 天 | 若 MVP 不收费，可后置 |
| AI 功能 | 5-15 天 | 若做引用、限额、成本统计，会更久 |

结论：

```text
不做支付和 AI：1 周内可以整理到可试用。
做支付：再加 1 周。
做 AI：至少再加 1-2 周。
```

### 4.3 最建议的节奏

1. 第 1 阶段：免费 MVP 上线，验证记录行为。
2. 第 2 阶段：加图片限制、导出、基础 Pro 权益。
3. 第 3 阶段：加支付。
4. 第 4 阶段：只给付费用户加 AI。

不要反过来。先做支付和 AI，会让产品还没验证就背上复杂度。

## 5. 盈利模式

### 5.1 推荐模式：Freemium + Pro 订阅

免费用户能完成主流程，但有限制。

Pro 用户获得更完整的长期记录能力。

建议权益：

| 能力 | 免费 | Pro |
| --- | --- | --- |
| 豆种档案 | 30 个 | 无限或高上限 |
| 购买批次 | 50 个 | 无限或高上限 |
| 冲煮记录 | 100 条 | 无限或高上限 |
| 日历照片 | 每月 30 张 | 每月 300 张 |
| 图片存储 | 低额度 | 高额度 |
| 统计 | 基础 | 高级趋势 / 过滤 |
| 导出 | 不支持或低频 | CSV / JSON 导出 |
| AI 复盘 | 不支持或每月 3 次 | 每月 50 次 |
| 自定义做法 | 10 个 | 无限或高上限 |

### 5.2 定价建议

建议先低价。

| 方案 | 价格建议 | 适合人群 |
| --- | ---: | --- |
| Free | $0 | 轻度记录用户 |
| Pro Monthly | $2.99-4.99 / 月 | 稳定记录用户 |
| Pro Yearly | $24.99-39.99 / 年 | 长期咖啡玩家 |
| AI Add-on | $2.99 / 包 | 高频 AI 用户 |

如果面向国内用户，价格可以做人民币版本：

| 方案 | 价格建议 |
| --- | ---: |
| Pro Monthly | ¥12-18 / 月 |
| Pro Yearly | ¥98-128 / 年 |
| AI 加量包 | ¥9.9 起 |

这里要注意：

1. 咖啡记录工具不是刚需办公软件，价格不能太高。
2. 付费理由最好绑定真实成本：照片、导出、高级统计、AI。
3. 不建议把基础记录能力完全锁死。否则用户无法形成数据资产。

### 5.3 其他盈利方式

| 模式 | 是否建议 | 原因 |
| --- | --- | --- |
| 一次性买断 | 可考虑 | 适合独立工具，但持续存储成本需要覆盖 |
| 赞助 / Buy me a coffee | 可早期使用 | 实现简单，但收入不稳定 |
| 联盟返佣 | 后续考虑 | 可对接咖啡豆购买链接，但要避免影响产品中立性 |
| 广告 | 不建议 | 会破坏记录工具体验 |
| 商城 | 不建议 MVP | 复杂度太高，会变成另一个产品 |
| B2B 给咖啡馆 | 后续考虑 | 需要团队、库存、员工权限，不是当前 MVP |

推荐顺序：

```text
免费 MVP -> Pro 订阅 -> AI 加量包 -> 导出/高级统计 -> 返佣
```

## 6. 网站内部收费功能怎么处理

### 6.1 原则

收费功能不能只靠前端隐藏按钮。

必须做到：

1. 前端显示权益状态。
2. 后端保存用户权益。
3. 支付成功后由 webhook 更新权益。
4. 服务端校验额度。
5. 超额时阻止写入或提示升级。

### 6.2 推荐技术方案

如果使用 Stripe：

```text
用户点击升级
  -> 前端创建 checkout session
  -> 跳转 Stripe Checkout
  -> 用户付款
  -> Stripe webhook 通知后端
  -> 后端更新 user_entitlements
  -> 前端刷新权益
```

当前项目纯前端直连 Supabase，不适合直接在前端处理支付密钥。

需要新增一个服务端层，二选一：

1. Supabase Edge Functions。
2. 独立轻量 Node / serverless API。

推荐先用 Supabase Edge Functions，减少架构变化。

### 6.3 需要新增的数据表

建议新增：

```text
plans
user_subscriptions
user_entitlements
usage_counters
billing_events
```

字段草案：

【plans】
- `id`
- `code`: free / pro_monthly / pro_yearly
- `name`
- `price_cents`
- `currency`
- `billing_interval`
- `active`

【user_subscriptions】
- `id`
- `user_id`
- `provider`: stripe / lemon_squeezy / paddle / manual
- `provider_customer_id`
- `provider_subscription_id`
- `plan_code`
- `status`: active / trialing / past_due / canceled / expired
- `current_period_start`
- `current_period_end`

【user_entitlements】
- `user_id`
- `plan_code`
- `max_beans`
- `max_batches`
- `max_brews`
- `monthly_photo_limit`
- `storage_limit_mb`
- `monthly_ai_limit`
- `can_export`
- `can_use_advanced_stats`

【usage_counters】
- `user_id`
- `month`
- `photo_upload_count`
- `photo_storage_mb`
- `ai_request_count`
- `ai_cost_cents`

【billing_events】
- `id`
- `provider`
- `event_type`
- `provider_event_id`
- `payload`
- `processed_at`

### 6.4 权益校验点

| 功能 | 校验点 | 免费限制示例 |
| --- | --- | --- |
| 新增豆种 | 保存前 | 最多 30 个 |
| 新增批次 | 保存前 | 最多 50 个 |
| 新增冲煮 | 保存前 | 最多 100 条 |
| 上传照片 | 上传前 + 上传后 | 每月 30 张，单张 500 KB |
| AI 复盘 | 调用前 | 每月 3 次 |
| 导出 | 点击导出时 | 免费不可用 |
| 高级统计 | 页面进入或功能使用时 | 免费只看基础统计 |

这里要注意：

1. 限制必须在服务端执行。
2. 前端只负责展示“你已用 20/30 张照片”。
3. 用户不能通过改前端代码绕过限制。

### 6.5 MVP 是否要现在做收费

不建议。

原因：

1. 当前更重要的是验证用户是否持续记录。
2. 支付会引入 webhook、权益、账单、退款、订阅状态等复杂度。
3. 收费功能如果过早，会干扰产品主流程验证。

建议收费触发条件：

1. 有 50 个以上稳定用户。
2. 有用户连续 4 周记录。
3. 图片存储成本开始明显增长。
4. 至少 5-10 个用户明确表示愿意为容量、导出或 AI 付费。

## 7. 场景测算

### 7.1 场景 A：内测 50 人

假设：
- 50 人注册。
- 20 人活跃。
- 活跃用户每月 20 条冲煮。
- 活跃用户每月 10 张照片，每张压缩 300 KB。

成本：

| 项目 | 估算 |
| --- | ---: |
| 前端部署 | $0 |
| Supabase | $0-25 |
| 域名 | $1-2 |
| AI | $0 |
| 支付 | $0 |
| 图片新增 | 20 * 10 * 300 KB = 60 MB / 月 |

结论：几乎没有压力。

### 7.2 场景 B：早期 1,000 注册用户

假设：
- 1,000 注册。
- 200 月活。
- 月活每月 20 条冲煮。
- 月活每月 20 张照片，每张压缩 300 KB。

图片新增：

```text
200 * 20 * 300 KB = 1.2 GB / 月
```

成本判断：

1. 数据库仍不是问题。
2. 照片开始需要监控，但可控。
3. Supabase Pro 更稳。
4. 仍不需要自建服务器。

月成本估计：

```text
$30 左右起步，视图片流量和 Supabase 超额而变化。
```

### 7.3 场景 C：10,000 注册用户

假设：
- 10,000 注册。
- 2,000 月活。
- 月活每月 20 张照片，每张压缩 300 KB。

图片新增：

```text
2,000 * 20 * 300 KB = 12 GB / 月
```

这时需要：

1. 强制图片压缩。
2. 区分免费 / 付费容量。
3. 监控 Storage egress。
4. 可能需要把图片改为更便宜或更可控的对象存储。
5. 考虑 Pro 订阅覆盖成本。

## 8. 收入测算

假设 Pro 定价 $3.99 / 月。

| 注册用户 | 月活 | 付费率 | 付费用户 | 月收入 |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 200 | 2% 注册转付费 | 20 | $79.8 |
| 5,000 | 1,000 | 3% 注册转付费 | 150 | $598.5 |
| 10,000 | 2,000 | 5% 注册转付费 | 500 | $1,995 |

扣除 Stripe 交易费用后：

以 $3.99 月付为例，单笔 Stripe 美国卡费用约：

```text
$3.99 * 2.9% + $0.30 = $0.416
```

单用户实收约：

```text
$3.99 - $0.416 = $3.57
```

所以低客单价月付会被固定手续费吃掉不少。

建议：

1. 强推年付。
2. 月付可以保留，但不要作为唯一模式。
3. 年付能显著降低手续费占比。

以 $29.99 年付为例：

```text
$29.99 * 2.9% + $0.30 = $1.17
实收约 $28.82
```

手续费占比从月付约 10% 降到年付约 4%。

## 9. 盈亏平衡粗算

假设稳定小规模成本：

| 项目 | 月成本 |
| --- | ---: |
| Supabase Pro | $25 |
| 域名均摊 | $2 |
| 部署 | $0 |
| 监控等杂项 | $0-10 |
| 合计 | $27-37 |

若 Pro 月付实收约 $3.57：

```text
$37 / $3.57 ≈ 11 个付费用户
```

结论：

1. 只要有 10-20 个稳定付费用户，就能覆盖早期基础设施成本。
2. 如果加 AI，要重新计算。
3. 如果照片无压缩，成本会更早失控。

## 10. 具体建议

### 10.1 MVP 阶段

1. 不收费。
2. 不接 AI。
3. 图片先做压缩和大小限制。
4. 免费用户也能完整体验主流程。
5. 记录用户行为：创建豆种、创建批次、创建冲煮、打开日历、上传照片。

### 10.2 第一版收费

只做一个 Pro。

Pro 卖点：

1. 更多图片额度。
2. 高级统计。
3. 数据导出。
4. 更多做法模板。
5. 后续 AI 复盘额度。

不要一开始做多档位。

### 10.3 第二版收费

当 AI 功能上线后：

1. Pro 包含基础 AI 次数。
2. 高频用户购买 AI 加量包。
3. 每次 AI 任务记录成本。
4. 超额时明确提示。

### 10.4 面向国内支付的处理

如果主要面向中国大陆用户，支付会比海外卡复杂。

可能路径：

1. 早期先不接支付，用免费内测。
2. 如果必须收费，先用人工收款 + 手动开通 Pro，验证付费意愿。
3. 正式自动收费再评估微信支付 / 支付宝 / 第三方 Merchant of Record。
4. 若使用国内支付和国内服务器，要同步考虑备案、主体、支付商户、合规要求。

如果主要面向海外用户：

1. Stripe Checkout 是最省开发的方式。
2. 使用 Stripe Customer Portal 处理订阅取消、付款方式更新、发票。
3. 用 webhook 同步订阅状态。

## 11. 上线前必须做的成本保护

1. 图片上传前压缩。
2. 单张图片大小限制。
3. 每用户每月上传张数限制。
4. 每用户总存储上限。
5. Supabase 项目费用告警。
6. 如果接 AI，必须有每用户每月次数限制。
7. 付费状态必须由服务端和数据库控制。
8. 禁止把支付密钥放前端。
9. 禁止前端自己判断是否付费后就开放高成本功能。
