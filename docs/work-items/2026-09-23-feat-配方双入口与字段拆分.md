## 一、背景与问题

### 当前问题

当前配方库将冲煮做法和咖啡饮品放在同一个字段模型中。`recipes.device` 同时承载 V60、法压、Espresso、美式、拿铁和冷萃等值，导致：

1. 美式和拿铁被错误地呈现为“器具”。
2. 咖啡饮品表单出现水温、粉量、液量、粉水比和总时间等不适用字段。
3. 配方列表同时混合冲煮做法和饮品，用户需要通过类型筛选才能理解内容。
4. 内置配方只有一个 `name` 字段，中文和英文界面无法显示不同名称。
5. 饮品和冲煮做法的后续筛选、统计和内容维护边界不清晰。

### 用户需求

- 用户可以从两个小入口分别查看冲煮做法和咖啡饮品。
- 用户创建冲煮做法时填写完整的冲煮参数。
- 用户创建咖啡饮品时只填写饮品类型、原料、步骤和说明。
- 冷萃可以同时作为一种浸泡方法和一种成品饮品保存。
- 内置配方在中文/英文模式下显示对应名称。
- 历史冲煮记录和原有设备选择不能被破坏。

## 二、目标与非目标

### 目标

1. 在 `/recipes` 顶部提供“冲煮做法”和“咖啡饮品”两个小入口。
2. 通过 `recipe_kind` 和字段约束实现两类配方的数据隔离。
3. 冲煮做法保留完整冲煮参数和“开始冲煮”入口。
4. 咖啡饮品不展示、不保存器具和冲煮参数。
5. 为内置配方增加中英文名称，为用户配方保留单一自定义名称。
6. 保留图片、原料、步骤、复制、私有配方和 RLS 逻辑。

### 不在范围内

- 不修改历史 `brew_records` 的 `device` 和冲煮参数。
- 不新增“饮品制作记录”表。
- 不让饮品配方进入库存扣减流程。
- 不开放用户配方公开投稿、评论、点赞、收藏或 Feed。
- 不开发内置配方后台管理系统。
- 不删除旧 `brew_device` 枚举值 `americano`、`latte`、`cold_brew`。
- 不改变现有图片数量、压缩、Storage bucket 和 RLS 方案。

## 三、产品交互方案

### 3.1 列表入口和路由

继续使用同一个页面组件 `RecipesList`，通过查询参数区分入口：

```text
/recipes?kind=brew_method
/recipes?kind=drink
```

规则：

- 没有 `kind` 或值非法时，默认显示 `brew_method`。
- 顶部使用两个紧凑的分段入口，不新增第二套列表页面。
- 切换入口时更新 URL，同时清空搜索、器具筛选和饮品类型筛选。
- 新建按钮根据当前入口跳转 `/recipes/new?kind=brew_method` 或 `/recipes/new?kind=drink`。
- 继续保留内置配方和我的配方两个分组。

### 3.2 冲煮做法列表

只显示 `recipe_kind = brew_method` 的记录。

- 搜索匹配 `name`、`name_zh`、`name_en`。
- 按 V60、Origami、Kalita、法压壶、爱乐压、意式、冷萃浸泡法、其他筛选。
- 卡片显示当前语言名称、另一语言名称、器具和关键参数。
- 显示“查看”和“冲一杯”按钮。
- 内置配方显示“内置”标识和复制按钮。

### 3.3 咖啡饮品列表

只显示 `recipe_kind = drink` 的记录。

- 搜索匹配 `name`、`name_zh`、`name_en`。
- 按美式、冰美式、拿铁、脏拿铁、摩卡、冷萃、柑橘美式、其他筛选。
- 卡片显示当前语言名称、另一语言名称、饮品类型和原料数量。
- 不显示器具、研磨度、水温、粉量、液量、比例和时间。
- 不显示“冲一杯”按钮。
- 内置配方显示“内置”标识和复制按钮。

### 3.4 冲煮做法表单

展示：做法名称、器具、默认研磨度、默认水温、默认粉量、默认液量、默认粉水比、默认总时间、默认注水方案、默认滤纸、做法说明和最多 5 张图片。

器具使用专用的 `RECIPE_BREW_DEVICES`，不把美式和拿铁作为配方器具；冷萃浸泡法保留为冲煮做法选项。

保存规则：

- `recipe_kind = brew_method`
- `device` 必填
- `drink_type = null`
- `drink_type_custom = null`
- 冲煮参数按用户填写值保存

### 3.5 咖啡饮品表单

只展示：饮品名称、饮品类型、自定义饮品类型、原料动态列表、制作步骤动态列表、做法说明和最多 5 张图片。

固定饮品类型：

```text
americano / iced_americano / latte / dirty_latte
mocha / cold_brew / citrus_americano / other
```

选择 `other` 时必须填写 `drink_type_custom`。

保存规则：

- `recipe_kind = drink`
- `device = null`
- `drink_type` 必填
- `drink_type_custom` 仅在 `drink_type = other` 时保存
- `default_grind`、`default_temp_c`、`default_dose_grams`、`default_yield_ml`、`default_ratio`、`default_time_seconds`、`default_pour_scheme`、`default_filter` 全部写入 `null`
- 原料、步骤和说明按用户填写值保存

### 3.6 详情和冲煮入口

- 冲煮做法详情显示器具和完整参数。
- 咖啡饮品详情只显示饮品类型、原料、步骤、说明和图片。
- 只有 `brew_method` 显示“冲一杯”按钮。
- `BrewForm` 只加载 `recipe_kind = brew_method` 的配方。
- 从配方进入冲煮时继续带入冲煮做法默认参数。
- 饮品详情不能进入库存扣减型冲煮记录。

### 3.7 冷萃规则

允许同时存在两条不同配方：

1. 冲煮做法“冷萃浸泡法”：`device = cold_brew`，保存粉量、液量、比例和时间等方法参数。
2. 咖啡饮品“冷萃”：`drink_type = cold_brew`，器具为空，保存原料和制作步骤。

两条记录不互相覆盖，也不通过名称做唯一约束。

## 四、名称维护方案

### 数据字段

```text
recipes.name       兼容旧数据及用户自定义配方名称
recipes.name_zh    内置配方中文名称
recipes.name_en    内置配方英文名称
```

### 显示规则

- 中文模式：优先 `name_zh`，其次 `name_en`，最后 `name`。
- 英文模式：优先 `name_en`，其次 `name_zh`，最后 `name`。
- 内置配方在列表和详情显示当前语言名称，并可显示另一语言名称。
- 用户自定义配方只填写 `name`，中英文模式都显示该名称。
- 搜索同时匹配三个名称字段。

### 维护位置

- 内置名称在 Supabase migration/seed 中维护。
- 页面组件不写死内置配方名称。
- 复制内置配方后成为用户私有配方，复制当前显示名称，`name_zh` 和 `name_en` 为空。

## 五、数据模型与数据库迁移

### 新增字段

`recipes` 新增 `name_zh text`、`name_en text`、`drink_type public.drink_type`、`drink_type_custom text`；`recipes.device` 改为允许为空。

新增 enum：

```text
public.drink_type:
americano, iced_americano, latte, dirty_latte,
mocha, cold_brew, citrus_americano, other
```

### 数据约束

数据库增加 `recipes_kind_fields_check`：

- `brew_method` 必须有 `device`，饮品字段为空。
- `drink` 必须有 `drink_type`，`device` 为空。
- `drink_type = other` 时自定义类型非空。
- `drink` 的研磨度、水温、粉量、液量、比例、时间、注水方案和滤纸全部为空。

### 历史迁移

Migration：`supabase/migrations/20260923120000_004_recipe_kind_split.sql`

迁移步骤：

1. 创建 `drink_type` enum。
2. 增加双语名称和饮品字段。
3. 将历史内置美式、拿铁、冰美式、脏拿铁、柑橘美式转换为 `drink`。
4. 清空这些饮品的器具和冲煮参数。
5. 为内置配方补充中文名和英文名。
6. 保留原有 Cold Brew 冲煮做法。
7. 新增 Cold Brew Drink 内置饮品。
8. 不修改历史 `brew_records`。
9. 保留旧 `brew_device` enum 值。
10. 为新饮品写入内置图片记录。

### RLS、Storage 与 Auth

- 不修改既有 `recipes`、`recipe_images` RLS policy。
- 不新增 Storage bucket。
- 不修改 Auth 配置。
- 内置配方对所有登录用户可见，用户配方仍只能本人访问。

## 六、代码实现约定

### 类型层

新增 `DrinkType`：

```ts
type DrinkType =
  | 'americano' | 'iced_americano' | 'latte' | 'dirty_latte'
  | 'mocha' | 'cold_brew' | 'citrus_americano' | 'other';
```

`Recipe` 增加 `name_zh`、`name_en`、`drink_type`、`drink_type_custom`，并将 `device` 调整为可空。

新增 helper：

```ts
getRecipeDisplayName(recipe, language)
getDrinkTypeLabel(type, custom, t)
getRecipeDeviceLabelT(device, t)
```

保留 `BREW_DEVICES` 给冲煮记录使用，新增 `RECIPE_BREW_DEVICES` 给配方表单和配方筛选使用。

### 服务层

`src/lib/utils.ts` 负责读取新字段、兼容旧数据、创建/更新前归一化字段、复制类型/名称/原料/步骤/图片，并保证饮品不进入冲煮流程。服务层不直接显示 toast。

## 风险与回滚方案

| 风险 | 影响 | 预防 | 回滚 |
| --- | --- | --- | --- |
| 历史 recipe 字段迁移不完整 | 旧配方无法展示或编辑 | 迁移前备份并保留旧字段 | 回滚 migration 或恢复备份 |
| 饮品字段残留冲煮参数 | 列表和详情出现错误信息 | 保存前按 recipe_kind 归一化并增加数据库约束 | 回滚类型归一化逻辑 |
| 内置配方名称缺失 | 中英文界面显示空名称 | 缺失时回退到 name | 回退到旧 name 显示 |
| 饮品进入冲煮流程 | 错误扣减库存 | BrewForm 只查询 brew_method | 恢复选择器并关闭饮品入口 |
