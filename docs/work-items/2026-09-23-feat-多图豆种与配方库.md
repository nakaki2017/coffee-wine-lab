## 2. 背景

豆种档案目前只有单个外部图片 URL，不能表达包装正面、背面和标签。现有做法模板也无法同时承载冲煮参数、饮品原料、步骤和成品图。

产品需要建立两个边界清晰的图片和配方能力：

- 豆种档案：最多 3 张图片，支持封面和排序。
- 配方库：最多 5 张图片，支持冲煮做法和咖啡饮品。
- 内置配方：所有登录用户可见。
- 用户配方：只对创建者本人可见。
- 图片保存为 Supabase Storage path，页面按需生成 signed URL。

## 3. 当前问题或用户需求

- 用户无法记录完整的豆种包装信息。
- 外部图片 URL 不受平台控制，可能失效，也缺乏权限边界。
- 配方图片、原料、步骤和冲煮参数没有统一模型。
- 内置配方和用户私有配方的读取、复制、修改边界需要明确。
- 移动端上传大图会增加等待时间和 Storage 成本。

## 4. 用户故事

- 作为咖啡记录用户，我希望给一个豆种保存多张包装图，以便日后识别和复购。
- 作为配方使用者，我希望查看内置配方的图片、原料和步骤。
- 作为配方作者，我希望保存自己的饮品配方，但不希望其他用户看到。
- 作为系统维护者，我希望内置配方不能被普通用户修改或伪装。
- 作为移动端用户，我希望图片上传前自动压缩并看到明确的失败提示。

## 5. 目标

1. 豆种最多保存 3 张图片，支持上传、删除、排序和设置封面。
2. 配方最多保存 5 张图片，支持上传、删除、排序和设置封面。
3. 配方支持原料、用量、单位和有序制作步骤。
4. 保留冲煮做法的完整参数，并让咖啡饮品不进入库存扣减型冲煮。
5. 使用私有 Storage、signed URL 和严格 RLS。
6. 保留现有 bean_profiles.image_url、历史配方和历史冲煮的兼容性。

## 7. 当前行为与目标行为

| 场景 | 当前行为 | 目标行为 |
| --- | --- | --- |
| 豆种图片 | 单个外部 URL | 最多 3 张受控图片，第一张为封面 |
| 配方图片 | 无统一图片管理 | 最多 5 张图片和排序 |
| 配方结构 | 主要是冲煮参数和说明 | 参数、原料、步骤按类型使用 |
| 内置配方 | 页面可见性和图片来源不统一 | 登录用户可读，普通用户不可改 |
| 用户配方 | 需要明确私有隔离 | 仅创建者本人可见和维护 |
| 图片访问 | 直接依赖外部 URL | 数据库存 path，按需生成 signed URL |

## 8. 页面和用户流程

### 8.1 豆种图片

1. 用户创建或编辑豆种。
2. 基础信息先保存，获得 bean_id。
3. 用户选择本地图片，前端校验类型和大小。
4. 浏览器压缩并转换为 WebP，最长边建议 1600px。
5. 上传到 bean-images/{user_id}/{bean_id}/{uuid}.webp。
6. 写入 bean_images，保存 sort_order。
7. 用户可删除、排序或设置封面。
8. 详情页显示横向相册，列表页只显示封面。

替换图片时先上传新图，数据库更新成功后再删除旧 Storage 文件，避免上传失败造成原图片丢失。

### 8.2 配方图片

1. 用户进入配方新建、编辑或详情页。
2. 根据配方权限判断是否允许修改图片。
3. 上传前压缩并校验最多 5 张。
4. 用户配方写入用户路径；内置配方由受控发布流程写入 builtin 路径。
5. 列表显示封面，详情显示最多 5 张图。
6. 删除配方时清理对应图片记录和 Storage 对象。

### 8.3 内置配方复制

1. 用户查看内置配方。
2. 点击复制。
3. 复制基础字段、原料、步骤和冲煮参数。
4. 将图片复制到当前用户自己的 Storage 路径。
5. 创建新的 recipe_images 记录。
6. 新记录设置 user_id 为当前用户、is_default=false。
7. 用户只能编辑和删除自己的副本。

不能直接引用内置图片路径，避免内置内容变化影响用户副本。

## 9. 字段、状态和业务规则

### 豆种图片

- 最多 3 条。
- sort_order 仅允许 0、1、2。
- sort_order=0 为封面。
- upload 类型必须有 storage_path。
- external_url 类型必须有 external_url。
- 每张图压缩后不超过 800KB，Bucket 上限建议为 1MB。
- 允许 jpg、jpeg、png、webp，上传后统一转换 WebP。

### 配方图片

- 最多 5 条。
- sort_order 仅允许 0 至 4。
- sort_order=0 为封面。
- 内置图片普通用户只能读取，不能修改或删除。
- 用户图片只能由所属用户读取、修改和删除。
- 数据库不永久保存会过期的 signed URL。

### 配方权限

- user_id=null 且 is_default=true：系统内置配方。
- user_id=当前用户且 is_default=false：用户私有配方。
- 普通用户不能创建或修改 is_default=true 的配方。

## 10. 交互和视觉要求

- 图片槽位固定尺寸，避免上传后布局跳动。
- 上传中显示进度或明确的 loading 状态。
- 超过数量、类型不支持、压缩失败和权限错误都显示可理解的错误提示。
- 图片加载失败显示默认占位图。
- 删除、替换和复制需要确认或明确 toast。
- 中文/英文、深色模式和 390px 移动视口都必须可用。
- 页面层管理预览、loading 和 toast；服务层不直接显示 toast。

## 11. 技术方案

### 数据表

新增 bean_images 和 recipe_images。

recipes 增加 recipe_kind、ingredients、steps；后续配方类型拆分任务增加 drink_type、name_zh、name_en 等字段。

### Storage

新增私有 Bucket：

~~~text
bean-images
recipe-images
~~~

路径：

~~~text
bean-images/{user_id}/{bean_id}/{uuid}.webp
recipe-images/user/{user_id}/{recipe_id}/{uuid}.webp
recipe-images/builtin/{recipe_id}/{uuid}.webp
~~~

### 服务层

在 src/lib/utils.ts 统一提供：

- fetchBeanImages
- uploadBeanImage
- deleteBeanImage
- reorderBeanImages
- fetchRecipe
- fetchRecipeImages
- uploadRecipeImage
- deleteRecipeImage
- reorderRecipeImages

服务层负责文件校验、压缩后的上传、path 生成、signed URL、旧文件清理和失败回滚。

## 14. 风险与回滚方案

| 风险 | 影响 | 预防 | 回滚 |
| --- | --- | --- | --- |
| 图片上传成功但数据库写入失败 | 遗留 Storage 文件 | 失败时清理新文件 | 保留旧图片，清理孤儿文件 |
| 图片替换时先删除旧图 | 原图丢失 | 先上传和写入新图 | 恢复旧 path |
| RLS 配置错误 | 越权读取或无法读取 | 使用多测试账号验证 | 回滚 policy migration |
| signed URL 过期 | 图片暂时无法展示 | 页面按需重新生成 | 回退为重新请求 URL |
| 大图导致移动端等待 | 体验和成本恶化 | 前端 WebP 压缩和大小限制 | 拒绝超限文件 |
